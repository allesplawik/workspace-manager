# Instalacja i testy RC2 na macOS Intel i Ubuntu 24.04

Użyj tych samych plików RC2 na obu hostach. Na macOS potwierdź `uname -m` = `x86_64` i wersję przez `sw_vers`. Na natywnym Ubuntu odczytaj `/etc/os-release` i `uname -m`. Zapisz nazwę i wersję emulatora, `python3.12 --version`, `git --version`, `tmux -V`, `codex --version` oraz `claude --version`. Na Ubuntu zainstaluj brakujące zależności systemowe, np. `sudo apt install python3.12 python3.12-venv git tmux zsh`. Na macOS użyj istniejącego Pythona 3.12 oraz Git i tmux dostępnych w PATH.

## 1. Osobna instalacja i zachowanie istniejących danych

Na Macu pliki są w `features/production-readiness/3.0.0rc2/` w zintegrowanym worktree. Skopiuj do katalogu na Ubuntu trzy artefakty wymienione w `SHA256SUMS`, sam plik sum oraz `smoke.py` i `migration.py`. To pliki testowe i instalacyjne, bez konfiguracji ani poświadczeń.

Z terminala poza tmux wykonaj poniższe kroki, podstawiając bezwzględną ścieżkę do katalogu pobranych plików. Instalacja używa osobnego venv. Ręczny fixture używa odrębnych XDG, katalogu roboczego oraz backendu tmux. Do prób agentów pozostaje dostępne własne logowanie użytkownika, bo HOME się nie zmienia.

```sh
export WM_RC_ARTIFACTS="/pełna/ścieżka/do/3.0.0rc2"
cd "$WM_RC_ARTIFACTS"
if command -v sha256sum >/dev/null; then
  sha256sum -c SHA256SUMS
else
  shasum -a 256 -c SHA256SUMS
fi
```

Kontynuuj po zobaczeniu trzech wpisów `OK`. Wykonaj w dedykowanej karcie terminala:

```sh
export WM_RC_ROOT="$(cd "$(mktemp -d /tmp/wm-rc2-manual.XXXXXX)" && pwd -P)"
python3.12 -m venv "$WM_RC_ROOT/venv"
. "$WM_RC_ROOT/venv/bin/activate"
python -m pip install "$WM_RC_ARTIFACTS/workspace_manager-3.0.0rc2-py3-none-any.whl"
python -c 'from importlib.metadata import version; from workspace_manager.tui import Manager; assert version("workspace-manager") == "3.0.0rc2" and Manager.CSS_PATH.is_file(); print(version("workspace-manager"))'

export XDG_CONFIG_HOME="$WM_RC_ROOT/config"
export XDG_STATE_HOME="$WM_RC_ROOT/state"
export TMUX_TMPDIR="$WM_RC_ROOT/tmux"
mkdir -p "$XDG_CONFIG_HOME/workspace-manager" "$XDG_STATE_HOME" "$TMUX_TMPDIR" "$WM_RC_ROOT/source"
chmod 700 "$TMUX_TMPDIR"
cat > "$XDG_CONFIG_HOME/workspace-manager/config.toml" <<EOF_CONFIG
work_root = "$WM_RC_ROOT/work"
source_root = "$WM_RC_ROOT/source"
default_agent = "shell"
EOF_CONFIG
```

Przy ponownym wejściu użyj tych samych wartości `WM_RC_ROOT`, XDG i `TMUX_TMPDIR`. Nie twórz ponownie fixture w tym samym katalogu. Powrót do normalnej instalacji po tym teście polega na wyjściu z dedykowanej karty lub powłoce bez jej zmiennych. Własne dane i sesje pozostają dostępne w oryginalnej konfiguracji.

## 2. Czysty smoke w emulatorze

Przygotuj fixture raz:

```sh
for repo in repo-a repo-b; do
  repo_path="$WM_RC_ROOT/source/$repo"
  git init -b main "$repo_path"
  printf '%s\n' "$repo" > "$repo_path/seed.txt"
  git -C "$repo_path" add seed.txt
  git -C "$repo_path" -c user.name='WM RC' -c user.email='wm-rc@example.invalid' commit -m 'Seed RC fixture'
done
wm workspace create rc-test --yes
for repo in repo-a repo-b; do
  wm repo add rc-test --source "$WM_RC_ROOT/source/$repo" --name "$repo" --branch "topic-$repo" --yes
done
wm workspace create rc-anchor --yes
wm terminal new rc-anchor --provider shell
wm --help
wm doctor
wm workspace list
wm workspace status rc-test
wm workspace select rc-test --print-path
. "$VIRTUAL_ENV/share/workspace-manager/wm.sh"
wmcd rc-test
pwd
```

Pozostaw Shell w `rc-anchor` do końca próby Git. Utrzymuje prywatny backend włączony po zakończeniu wszystkich sesji `rc-test`, dzięki czemu WM może zweryfikować stan przed operacją Git.

Oczekuj listy TSV, statusu JSON i tej samej ścieżki w `--print-path` i `pwd`. Powtórz `wmcd nieistniejacy` i sprawdź `echo $?` oraz `pwd`. Oczekuj kodu 1 bez zmiany katalogu. Osobno wpisz `wm nieistniejaca-komenda` i sprawdź kod 2.

Otwórz kolejno `wm`, `wm split` i `wm --classic` w tym emulatorze. W dwóch pierwszych przypadkach oczekuj Explorera i prawdziwego prawego terminala. Odłącz widok przez `Ctrl+B`, potem `d`. W klasycznym widoku wybierz workspace i otwórz testowy terminal, zakończ jego shell przez `exit` i potwierdź powrót do dashboardu. Wyjdź przez `q`. Wykonaj [próby Shell, agentów i Git](3.0.0-release-checklist.md#próby-ręczne-w-izolowanym-fixture). Próbę Git wykonaj na końcu, ponieważ usuwa worktrees fixture.

## 3. Aktualizacja i rollback na kopii danych

W dedykowanej karcie wykonaj z aktualnym venv RC2:

```sh
python3.12 -m venv "$WM_RC_ROOT/old"
"$WM_RC_ROOT/old/bin/python" -m pip install "$WM_RC_ARTIFACTS/workspace_manager-2.0.0-py3-none-any.whl"
python "$WM_RC_ARTIFACTS/smoke.py"
python "$WM_RC_ARTIFACTS/migration.py" "$WM_RC_ROOT/old/bin/wm" "$WM_RC_ROOT/venv/bin/wm"
```

Skrypty używają dodatkowego izolowanego HOME, XDG i socketów. Szukaj `PASS 2.0.0 -> rc2 -> restored 2.0.0, IDs/config/HEAD/cwd/PID unchanged`. Zapisz pełny wynik. Skrypt sprawdza kopię fixture, jawne dodanie backendu legacy, odmowę usunięcia używanego worktree oraz przywrócenie bajtowo tej samej konfiguracji i metadanych bez zmiany PID.

### Gdy chcesz później użyć RC2 ze swoim rzeczywistym stanem

1. Ustal ścieżkę konfiguracji `${XDG_CONFIG_HOME:-$HOME/.config}/workspace-manager/config.toml` oraz ścieżkę stanu z opcji `state` w tym pliku lub `${XDG_STATE_HOME:-$HOME/.local/state}/workspace-manager`. Polecenia `wm workspace list` i `wm workspace status <nazwa>` pokażą zarejestrowane katalogi. Przed zmianą zapisz też listę terminali, PID i cwd. Zachowaj poprzednią instalację.
2. Odłącz widok starego WM i wstrzymaj operacje zmieniające konfigurację, metadane lub Git. Zachowaj kopię pliku TOML, całego katalogu stanu oraz `.wm` każdego workspace, z zachowaniem ścieżek. Przykład do wykonania po wskazaniu prawdziwych wartości zmiennych: `cp -p "$CONFIG_FILE" "$BACKUP/config.toml"`, `cp -a "$STATE_DIR" "$BACKUP/state"` oraz `cp -a "$WORKSPACE/.wm" "$BACKUP/workspace-ID.wm"` dla każdego workspace. Zapisz odpowiadające ścieżki i ID. Zachowaj zwykły backup worktrees i repozytoriów, jeżeli planujesz modyfikacje Git. Metadane zawierają bezwzględne ścieżki. Kopia samych metadanych nie tworzy niezależnego drzewa danych produkcyjnych.
3. Z normalnego terminala z oryginalnymi XDG i socketami wywołaj absolutną ścieżką `/…/venv/bin/wm workspace list` i `/…/venv/bin/wm terminal backend-status <workspace>`. Porównaj ID, ścieżki, PID i cwd z zapisanymi wartościami. Jeśli używasz legacy socketów, obowiązuje [jawna rejestracja](3.0.0-release-notes.md#aktualizacja-i-powrót). Przy niepełnej weryfikacji zachowaj dane i wyjaśnij przyczynę przed wykonywaniem operacji Git. Po odłączeniu starego widoku uruchom RC2 tą samą absolutną ścieżką. Zostaw istniejące serwery tmux uruchomione i nie używaj `Terminate` wobec rzeczywistych sesji w smoke.
4. Przy powrocie odłącz RC2 i wstrzymaj operacje zapisujące. Jeżeli użyłeś tylko fixture, wróć po prostu do starego launchera. Jeżeli RC2 zapisywał rzeczywisty stan, zachowaj osobną kopię stanu po RC2 i uzgodnij późniejsze zmiany przed odtworzeniem. Kopię sprzed aktualizacji przywracaj w tych samych ścieżkach po odłożeniu bieżących plików. Nie przywracaj starej metadanej Git nad zmodyfikowanym worktree. Użyj zachowanego launchera i ponownie porównaj ID, ścieżki, HEAD, konfigurację, PID i cwd. Próba na kopii 2.0.0 została wykonana. Dokładna zgodność rzeczywistej konfiguracji zależy od jej zawartości i zarejestrowanych backendów.

## 4. Pełna regresja na natywnym hoście

Po weryfikacji sum uruchom z nowo rozpakowanego sdist, w odrębnym środowisku:

```sh
WM_SUITE="$(cd "$(mktemp -d /tmp/wm-rc2-suite.XXXXXX)" && pwd -P)"
tar -xzf "$WM_RC_ARTIFACTS/workspace_manager-3.0.0rc2.tar.gz" -C "$WM_SUITE"
cd "$WM_SUITE/workspace_manager-3.0.0rc2"
python3.12 -m venv "$WM_SUITE/venv"
"$WM_SUITE/venv/bin/python" -m pip install '.[dev]'
mkdir "$WM_SUITE/home" "$WM_SUITE/state" "$WM_SUITE/config" "$WM_SUITE/tmux" "$WM_SUITE/codex"
chmod 700 "$WM_SUITE/tmux"
"$WM_SUITE/venv/bin/ruff" check .
"$WM_SUITE/venv/bin/ruff" format --check .
"$WM_SUITE/venv/bin/mypy" src
env -u TMUX -u TMUX_PANE HOME="$WM_SUITE/home" XDG_STATE_HOME="$WM_SUITE/state" XDG_CONFIG_HOME="$WM_SUITE/config" TMUX_TMPDIR="$WM_SUITE/tmux" CODEX_HOME="$WM_SUITE/codex" PYTHONPATH=src "$WM_SUITE/venv/bin/python" -m pytest -q
```

Oczekuj braku błędów i sprawdź, czy wymagane testy nie zostały pominięte. Punktem odniesienia jest 180 testów i 35 subtestów na obu dotychczasowych środowiskach. Testy są z tego samego sdist, a próby instalacyjne i ręczne z tego samego wheel. Zapisz platformę, wynik, SHA-256, log i status każdego punktu [checklisty](3.0.0-release-checklist.md).
