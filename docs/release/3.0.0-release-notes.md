# Workspace Manager 3.0.0 — projekt informacji o wydaniu

## Co zmienia się od 2.0.0

- Interaktywny `wm` otwiera Explorer i rzeczywisty terminal tmux. `wm split` otwiera ten sam widok, a `wm --classic` uruchamia klasyczny dashboard.
- Explorer wybiera kontekst workspace lub worktree. Zakładki przełączają działające procesy i zachowują ich PID. Zamknięcie zakładki odłącza widok. **Terminate** wymaga potwierdzenia i zweryfikowanej własności panelu.
- Historia Codexa obsługuje filtrowanie według poświadczonego katalogu i lokalne tytuły. Claude Code wznawia rozmowy w natywnym pickerze. Resume uruchamia nowy proces z zapisaną rozmową. Reconnect wraca do istniejącego procesu.
- Workspace Memory jest wspólna dla workspace, a zapis weryfikuje rewizję. WM chroni używane lub zmodyfikowane worktrees i sprawdza zarejestrowane backendy tmux.
- Wheel dostarcza punkt wejścia `wm`, motyw TCSS i skrypt `wmcd` dla Bash i Zsh.

## Instalacja kandydata

W odrębnym środowisku z Pythonem 3.12+, Git i tmux sprawdź SHA‑256 według raportu RC, a następnie zainstaluj wheel.

```sh
python3.12 -m venv .venv-wm-rc
. .venv-wm-rc/bin/activate
python -m pip install /ścieżka/workspace_manager-3.0.0rc2-py3-none-any.whl
wm --help
wm doctor
wm
```

Dla `wmcd` załaduj `. "$VIRTUAL_ENV/share/workspace-manager/wm.sh"`. Codex CLI i Claude Code wymagają osobnej instalacji i autoryzacji. Oficjalna lista wspieranych platform powstanie po zakończeniu bramek RC.

## Aktualizacja i powrót

1. Ustal rzeczywiste ścieżki konfiguracji, rejestru stanu i metadanych `.wm` każdego workspace. Uwzględnij XDG i nadpisania w konfiguracji. Wstrzymaj operacje zmieniające dane WM i zachowaj kopię tych lokalizacji oraz używany plik instalacyjny starszej wersji.
2. Zainstaluj RC obok starszej wersji w osobnym środowisku Python. Najpierw sprawdź działanie na testowej kopii konfiguracji i izolowanych danych. Metadane zawierają bezwzględne ścieżki. Do prób migracji przygotuj kopię lub fixture z poprawnymi ścieżkami, a przy odtwarzaniu kopii przywróć metadane pod oryginalne ścieżki.
3. Sprawdź `wm terminal backend-status <workspace>`. Jeśli są używane niestandardowe historyczne sockety, zarejestruj każdy jawnie poleceniem `wm terminal backend-register <workspace> --socket /pełna/ścieżka.sock`. Użyj `--complete-legacy` dopiero gdy wszystkie znane backendy zostały sprawdzone. Sam wpis w rejestrze umożliwia obserwację, a starsze panele nadal podlegają ograniczeniom własności.
4. Przy powrocie odłącz widok WM i wstrzymaj zmiany w metadanych. Zachowaj kopię aktualnego stanu i odtwórz kopię sprzed aktualizacji w tych samych lokalizacjach. Uruchom zachowaną starszą wersję. Zweryfikuj ID i ścieżki workspace, katalogi i HEAD worktrees, konfigurację oraz PID i cwd istniejących terminali. Zmiany powstałe po aktualizacji wymagają osobnego uzgodnienia przed użyciem przywróconego rejestru. Procesy tmux pozostają aktywne podczas podmiany wersji programu.

W split kolizja lokalnego ID dwóch backendów wymaga zamknięcia istniejącej karty i otwarcia drugiego terminala. Oba procesy mogą nadal działać. Nowy widok może podłączyć żywy terminal po awarii serwera wyświetlania. Po zakończeniu serwera utrzymującego dany proces konieczne jest ponowne uruchomienie programu.

## Tagi kandydatów i artefakty z GitHub Actions

Po aktualizacji `main` CI uruchamia testy. Gdy cała macierz przejdzie, wywołuje workflow **Release artifacts**. Dla wersji zapisanej jako `X.Y.ZrcN` workflow wybiera numer o jeden wyższy od większej z dwóch wartości: `N` z pakietu i najwyższego istniejącego numeru RC w tej serii. Z bazą `3.0.0rc2` pierwszy taki build otrzyma więc co najmniej `3.0.0rc3`, co zachowuje numer dotychczasowego lokalnego RC2. Ponowne uruchomienie dla automatycznie otagowanego commita pomija budowę.

Workflow wpisuje obliczoną wersję tylko w kopii do budowy. Po sprawdzeniu wheela i udostępnieniu artefaktów tworzy tag na przetestowanej rewizji `main`. W **Actions → quality** pobierz wheel, sdist, `SHA256SUMS` i `BUILD-INFO.txt`. Ten ostatni plik wiąże wyliczony numer pakietu z SHA źródeł. Numery odzwierciedlają kolejność ukończenia CI i wejścia do kolejki. Jeśli zewnętrzna operacja zajmie numer przed utworzeniem tagu, GitHub odrzuci próbę. Ponowienie całego przebiegu obliczy nowy numer.

Automatyzacja obejmuje wyłącznie tagi RC i artefakty GitHub Actions. Stabilny tag `v3.0.0` oraz publikacja GitHub Release podlegają osobnej akceptacji zgodnie z [kontraktem wydania](3.0.0-release-contract.md).
